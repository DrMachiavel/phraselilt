# Evidence and assessment release gate

Current status: working local replay/reference/practice loop; **zero validated diagnostic findings**. Recognition-correct synthetic speech verifies data flow and approximate timing only. No consented human speech set has been evaluated, so false corrections, usefulness, pronunciation coverage and human-set abstention are **not measured**. The optional sound experiment offers tentative comparison targets, not validated diagnoses. No educational efficacy claim.

Before enabling acoustic diagnosis, collect consented clips outside the repository with separate permission for evaluation/storage, and human-reviewed intent and pronunciation expectations. Keep names and recordings private. Include:

- Clearly spoken spontaneous work sentences and retries with known wording.
- Recognition-correct clips with human-audible differences in sounds or stress.
- Legitimate General American, southern British and regional variants; accepted alternatives should not trigger correction.
- Ambiguous intended words such as browser/brother, confirmed by the speaker before assessment.
- Silence, clipping, low volume, background noise, input failures and difficult microphone conditions.
- Work vocabulary, acronyms, unfamiliar names and unseen speakers/language backgrounds.

Have qualified reviewers independently label supported corrections, acceptable variants, unclear evidence and useful practice targets. Resolve disagreement; do not force a single accent norm. Split development and held-out speakers. Evaluate the actual selected weights and acoustic feature pipeline, not just a scorer on precomputed features. Independently audit all source/model/dataset licenses and checkpoint loading safety.

Track per category: false corrections among acceptable variants; supported/useful suggestions rated by reviewers; missed supported opportunities; abstentions and reasons; end-to-end latency; peak app plus worker/system-service memory; model disk and download size. Preserve denominators and disagreement; do not invent confidence percentages or generalize from a tiny sample. Choose acceptance criteria with reviewers before viewing held-out results. If any category lacks evidence, abstain for it.

A synthetic pipeline sentence (“Please open the browser before the meeting.”) was correctly transcribed with seven timing segments on the development M5. First measured latency was 2.37 s, warm 0.36 s. A process-network-denied run succeeded with installed assets. The observed ~18 MB probe RSS excludes the speech daemon and shared model footprint; it is not total memory usage. This does not constitute a machine-wide offline test or coaching evaluation.

Release verification still needs human VoiceOver listening/focus review, real input-device changes, sleep/lock interruption, parallel-capture and source-boundary checks, noisy human speech, and a full machine-network-disabled run. Keep validated diagnostic claims unavailable while the acoustic gate remains unresolved.

Companion capture adds an independent release gate: public activity readability alone is insufficient. Validate concurrent input with the actual dictation app and hardware; assess onset truncation, trailing cutoff, standby microphone state, headset profiles and unchanged text insertion. See COMPANION.md. Audio from these checks stays outside the repository and CI.

## Narrow sound experiment: synthetic pipeline checks

User-authorized experimental comparison hints are available separately from diagnosis. Five short fixtures generated outside Git exercised the actual quantized ONNX model and native Swift rule path, with known synthetic word timings: a clear Samantha sentence, a deliberately altered Samantha sentence, a Daniel sentence, silence and seeded noise. All used the intended sentence “I think three things are ready.” Three candidate words were examined. Clear, Daniel, silence and noise produced no hints in this run. The altered sentence (“I sink free sings are ready”) produced one target, **th in think**, and missed the other two deliberate changes. Whole-phrase free decoding had also normalized “sink” toward theta, illustrating that acoustic recognizers can correct/hallucinate sounds and that cropping changes outputs. Do not treat model outputs as literal acoustic truth.

Observed native end-to-end model verification/load plus three short crops: 0.95 s first, 0.55–0.58 s subsequent runs on this M5; silence abstained before model loading in 0.003 s. Separate Python CPU inference took 0.16–0.20 s per approximately two-second whole clip after 0.62 s load, peak process RSS 863 MB. Native peak memory and concurrent system speech-service memory were not measured. Disk: 355,436,367 model/vocabulary bytes plus the runtime linked into the app. Settings recommends 1 GB free. These are pipeline timings on synthetic speech, not useful-feedback, precision, recall, accent-fairness or educational validation.

The five-fixture native model check also passed with process networking denied via `sandbox-exec`; this is not a machine-wide offline test. SwiftPM manifest sandboxing was disabled inside that already network-denied test process to avoid unsupported nested sandbox creation. The opt-in integration test is `PHRASELILT_SOUND_EVIDENCE_DIR=/absolute/private/fixture-directory swift test --filter localAcousticSyntheticSpike`. Generate the WAV fixtures with `python3 scripts/create-sound-fixtures.py /absolute/private/fixture-directory`, using installed Samantha/Daniel system voices; copy the explicitly downloaded pinned model/vocabulary there. Voice revisions can change synthetic timings; review any changed behavior rather than tuning thresholds to make a test green. The test uses known synthetic boundaries, not an ASR or human-evaluation claim; ordinary CI skips this model-dependent check. Unit tests cover confirmed intent and same-count corrections, exact timing, acoustic/context gating, corrupted model integrity and late-result cancellation. No personal recordings were accessed for this experiment.

Next gate: consented human recordings with qualified independent review, held-out speakers, accepted variants, sound substitutions and microphone/noise challenges. Until then the UI says “Compare”, never “incorrect”, and a no-hint result never means correct pronunciation. Coverage is deliberately limited to six words with American reference; British-reference analysis abstains.

The actual packaged sandboxed app was exercised through native accessibility controls: explicit model download, cancellation, retry to checksum-verified readiness, WAV import, intended-wording correction, Check Sounds and rendered amber underlined “th”. Using the same altered synthetic clip with real ASR word windows produced a target in **things**, rather than the **think** target with the hand-supplied test windows. This sensitivity to crop boundaries is a material limitation, not evidence of accurate localization. The UI visibly identifies the feature as experimental. Human VoiceOver auditory review, increased-contrast appearance, real noisy human speech and accepted-variant false-correction rates remain unverified for this new path.

## 0.3.1 automatic checks and compound timing

A reported failure was traced to one multi-token compound timing run causing the previous one-run-per-token guard to reject an otherwise separately timed “think”. A sanitized regression fixture uses “I think my mother-in-law is here.” and confirms that the target survives the compound, while a target inside a multi-token run still abstains. This fixes candidate eligibility, not acoustic accuracy. Automatic checks now accept provisional displayed wording without changing the persisted confirmation flag. Unit checks cover preparation blocking, first automatic request, unchanged-request deduplication, model enable/disable, replacement context and stale-result rejection. UI coverage remains the same narrow six-word experiment; absence of a highlight must not be interpreted as correct pronunciation.
